The same run detects seven conflicting files and records one. The six that disappear are
all the Scala files, covering both kinds: content conflicts (ReplicaManager.scala,
PartitionTest.scala, ReplicaManagerTest.scala) and modify/delete where the file is absent
from the target (UnifiedLog.scala, AddPartitionsToTxnManager.scala,

This affects the Git-CherryPick row as well as the RePatch row, so a reader comparing the two
tools inside this harness is comparing two numbers that both understate the conflict.

## 4. CORRECTION TO WHAT I WROTE IN THE INTERMEDIATE AND IN EARLIER DRAFTS

I previously wrote that scoping discarded the Log.scala -> UnifiedLog.scala rename
(KAFKA-13068, upstream db1f581da7). The database shows that is not what happened:

  SELECT COUNT(*) FROM refactoring;                                      -> 454
  SELECT COUNT(*) FROM refactoring WHERE refactoring_detail LIKE '%.scala%';   -> 0
  SELECT COUNT(*) FROM refactoring WHERE refactoring_detail LIKE '%nifiedLog%'
                                      OR refactoring_detail LIKE '%Log.scala%'; -> 0

Not one of the 454 detected refactorings mentions a Scala file. The rename was never
detected, so scoping had nothing to discard. The log line

  -> Scoped detection for fdb9fd013ad0fa86adb01c6d1d2852d396b93b04 to conflicting files: kept 0/120

refers to 120 Java refactorings, none of which touch the conflicting files.

The accurate statement is narrower and stronger: RefactoringMiner is Java-only, so RePatch
cannot assist any patch that edits Scala. Most of Kafka's broker code is Scala.
